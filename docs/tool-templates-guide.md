# ツール呼び出しの「文の型」の書き方

文の型を書く人向けの手引き。書く場所は `corpus/tool_sft_templates.toml`（このリポジトリには入っていない。公開していないので、自分で書く）。全体の方針は [tool-calling.md](tool-calling.md)。

## 何を書くのか

ツール呼び出しの学習データは、1件がこういう会話になる。

```
ユーザー    ：docs にファイルはいくつある？        ← 人が書く（依頼の型）
アシスタント：ls を呼ぶ {"path": "docs"}          ← プログラムが作る
ツール      ：README.md / guides/ / tools/       ← 実際に ls を走らせた結果
アシスタント：3 個です。                          ← 人が書く（答えの型）
```

人が書くのは、**依頼の文**と**答えの文**の2つだけ。ツールを呼ぶ部分と、ツールの結果は、プログラムが作る。

`{dir}` や `{n}` のような `{ }` の部分は「穴」で、プログラムが毎回ちがう値を入れる。型を1つ書くと、何百通りもの会話になる。

## ファイルの書き方

作業ごとに `[作業の名前]` の見出しがあり、その下に `request`（依頼）と `answer`（答え）の一覧を書く。

```toml
[ls_count]
request = [
  "{dir} にファイルはいくつある？",
  "{dir} の中、何個ある？",
]
answer = [
  "{n} 個です。",
]
```

決まりは4つ。

- 文は `"` で囲む。文と文の間は `,` で区切る。最後の `,` はあってもなくてもよい
- 改行したいときは `\n` と書く
- `{ }` は穴の印なので、文の中で `{` `}` そのものを使いたいときは `{{` `}}` と書く
- 行の頭に `#` を付けると、その行はメモになり、学習には入らない

## 作業と、使える穴

| 作業 | どういう依頼か | 依頼で使える穴 | 答えで使える穴 |
|---|---|---|---|
| `ls_count` | フォルダの中身の数をたずねる | `{dir}` | `{dir}` `{n}` |
| `ls_list` | フォルダの中身を並べてもらう | `{dir}` | `{dir}` `{n}` `{entries}` |
| `read_first_line` | ファイルの最初の行（見出し）をたずねる | `{path}` | `{path}` `{first_line}` |
| `read_lines` | ファイルの何行目から何行目かを見せてもらう | `{path}` `{start}` `{end}` | `{path}` `{start}` `{end}` `{content}` |
| `grep_files` | ある言葉が出てくるファイルを探してもらう | `{word}` `{dir}` | `{word}` `{dir}` `{files}` `{n}` |
| `grep_none` | 探したが見つからなかったとき | `{word}` `{dir}` | `{word}` `{dir}` |

穴に入る値の例。

- `{dir}`：`docs/guides`、`blog/2016`、`.`（いまいる場所）
- `{path}`：`examples/05-implementation.md`
- `{n}`：数字だけ（`3`）。「個」「件」は型のほうに書く
- `{entries}` `{files}`：`README.md、guides、tools` のように読点でつないだもの
- `{first_line}`：`# 仕様駆動開発 実践入門` のような1行
- `{content}`：読んだ行そのもの（何行にもなる）
- `{word}`：`フレディ`、`セキュリティ` のような短い言葉

`{dir}` に `.` が入ることがある。「. にファイルはいくつ？」は不自然なので、`{dir}` を使わない言い方（「ここに」「このフォルダに」）も混ぜておくとよい。

## よい型を書くこつ

**依頼の文**（学習の対象ではない。モデルが「読む」側）

- 言い方を散らす。丁寧（「教えてください」）、くだけた（「見せて」）、短い（「docs の中身」）、遠回し（「docs に何が入ってるか知りたい」）
- ふだん IXV に頼むときの言い方で書く。それがいちばん役に立つ
- 穴を使わない依頼は書かない。どのフォルダやファイルのことか、モデルにわからなくなる

**答えの文**（学習の対象。モデルが「まねる」側）

- 短く、事実だけ。ツールの結果にないことは書かない（「たくさんありますね」「便利なファイルです」などの感想や推測は入れない）
- 結果の値は、必ず穴で入れる。数や名前を型に直接書かない
- 言い方は2〜3通りで十分。依頼ほど散らさなくてよい
- `read_lines` の `{content}` は長いので、「{start} 行目から {end} 行目です。\n\n{content}」のように、前置きは短く

## どれくらい書くか

- 依頼：作業1つにつき **5〜10 個**
- 答え：作業1つにつき **2〜3 個**

全部で 50〜80 文くらい。1時間ほどで書ける量を見込んでいる。全部の作業がそろわないとデータは作れないので、まずは各作業に依頼2つ・答え1つから始めて、あとで足してもよい。

## 書いたら確かめる

```bash
.venv/bin/python corpus/make_tool_sft.py --check
```

- 書き方が崩れているところや、その作業で使えない穴を使っているところを、場所つきで教えてくれる
- 問題がなければ、作業ごとに1件ずつ、実際に組み立てた会話を見せてくれる。読んで不自然なら直す

確かめが通ったら、Claude に「型を書いた」と伝えてください。データを作って中身を見てもらい、学習に回します。

## 書かないでほしいもの

- Claude に書かせた文（Claude に直させたものも含む）。ほかの AI（IXV で動く DeepSeek や GLM など）に書かせるのはよい（README の方針は Claude についてだけ）。そのときは、モデルの名前を台帳の helper_models に書き、出力を学習に使ってよいライセンスかを確かめる。答えの文はモデルがまねるので、田中さんが目を通して直す
- 実在の人の名前、社外秘の話、パスワードなど（依頼の文にも入れない）

型の例はこの手引きに少し書いたが、例はそのまま使わず、自分の言い方で書いてください。例は Claude が書いた文なので、そのまま入れると学習データに Claude の文が入ってしまう。
